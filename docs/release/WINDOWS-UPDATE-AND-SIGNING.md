# Windows update and binary release gates

Preview.14 incorporates the repaired atomic pointer switch and API health polling. The public release gate now checks the packaged desktop executable as well as the installer, requires reviewer/date/build-instruction fields for the FFmpeg source bundle, and rejects self-signed QA certificates or signatures without a trusted timestamp.

Preview.15 adds the conditional online updater and bilingual update controls. Unsigned previews still expose only the official release link; the download/install controls appear only after a production-signed build and an eligible official release exist.

In the Windows 10 QA VM, preview.15 staged beside preview.14, upgraded through the verified helper, relaunched, and retained the existing three-shot project. Its unsigned release metadata kept online installation unavailable: both direct prepare and install requests returned HTTP 409 without closing the app. The final public download and graceful IPC shutdown path cannot be accepted until a production-signed release exists.

Clean Windows 10 VM development evidence: preview.12 to preview.13 staging, signed QA update, and post-upgrade project/render retention passed. An injected failure after pointer switching restored preview.12, restarted it, and retained the three-shot project. Incorrect hash, incorrect signer, and use of the QA certificate for public release were rejected. A production certificate and complete FFmpeg corresponding-source bundle are still absent; the final signed installer must be retested with its actual release certificate.

The preview.14 installer was then staged beside the running preview.13 and upgraded using the updater script taken from the staged package itself. Its hash matched the source script, the pointer advanced only after verification, the API reported preview.14, and the existing three-shot project remained readable. After a Windows reboot, the desktop shortcut launched preview.14 and both previous renders were still present. VM evidence is in the local `dist/vm-acceptance-20260929/guest-out` directory, which is deliberately excluded from the public source export.

The same VM then uninstalled a three-version program directory and reinstalled preview.14. Uninstall exit code was zero; the program folder and desktop shortcut were removed. The SQLite workspace and an exported MP4 had identical SHA-256 hashes before and after uninstall. Fresh installation relaunched preview.14 and reopened the original three-shot project.

Preview.13 introduces a staged installer layout. A new installer copies its files to `versions/<new-version>` and writes `staged.txt` while `current.txt` continues to select the working version. Desktop and Start shortcuts use the stable `Launch.ps1` entry. The previous version is retained until the signed update helper verifies all installed file hashes, changes `current.txt`, and observes the new local service. On probe failure the helper restores the previous pointer and starts the old version. The uninstaller removes the program directory and all retained versions; it does not touch `%LOCALAPPDATA%\Reelori\data`.

`scripts/apply-windows-update.ps1` only accepts an installer under `%LOCALAPPDATA%\Reelori\updates`. It requires an exact SHA-256 and a valid Authenticode signature from a pinned certificate thumbprint before executing the installer. It waits for the running app and local web port to stop. Source-mode callers must not supply an untrusted thumbprint. No production certificate is configured yet, so current unsigned builds keep online installation disabled and link to the official GitHub Release page.

The conditional online updater is enabled only when the running installed package identifies a pinned production signer. It reads GitHub's official latest-release API on request, requires an uploaded `reelori-<version>-setup.exe` and `ffmpeg-9.0.2-corresponding-source.tar.gz` asset with SHA-256 digests, downloads only from the official release path and allowed GitHub asset hosts, enforces a size limit, and verifies the installer hash and trusted Authenticode signature before showing “Install and restart.” The source asset's presence and digest are checked in the release metadata; its contents are reviewed by the publisher's release gate, not downloaded by each desktop app. Installation re-verifies the staged file, waits for the Electron app to exit through its IPC shutdown path, and uses the rollback helper. A new signing certificate requires a separately planned trust rotation; simply changing the online release signer will be rejected by existing installations. This path still needs acceptance with the final production-signed GitHub Release.

For a signed build, install a trusted code-signing certificate with its private key in the Windows certificate store and install Windows SDK SignTool. Set `REELORI_SIGN_CERT_THUMBPRINT` to its public thumbprint and optionally `REELORI_SIGNTOOL` to the SignTool executable. `npm run package:windows` signs `desktop/Reelori.exe` before creating the package manifest; `npm run build:installer` signs the installer. The signing script verifies Authenticode after signing. Do not commit private keys, PFX files, passwords, or timestamp credentials.

The pinned Gyan FFmpeg 9.0.2 essentials build is GPL-enabled and statically linked. `npm run audit:ffmpeg-sources` verifies the binary archive and the exact FFmpeg core source archive, then writes an inventory under `dist/ffmpeg-source-audit-9.0.2`. The verified core source archive is not a complete corresponding-source bundle: the upstream README lists 42 external libraries. Each still needs its exact source archive, license text, patches, and build recipe. The inventory deliberately has `readyForBinaryPublication: false` until reviewed.

`npm run release:verify-windows` is fail-closed. It requires `REELORI_FFMPEG_SOURCE_BUNDLE` to point to a complete, reviewed bundle with matching hashes for every listed library and `REELORI_SIGN_CERT_THUMBPRINT` to verify the signed installer. Passing that local gate is necessary but not sufficient: run clean Windows install, upgrade, rollback, render, and uninstall tests on the signed candidate and publish the source bundle beside the installer. The [FFmpeg legal checklist](https://ffmpeg.org/legal.html) calls for corresponding source and build instructions; the [Gyan 9.0.2 release](https://github.com/GyanD/codexffmpeg/releases/tag/9.0.2) identifies the FFmpeg core commit.
